# Python 类型注解、dataclass 与 Pydantic 验证机制

## 一、Python 类型注解（Type Hints）

### 1. 类型注解是什么？

Python 是动态类型语言，类型注解用于描述变量、函数参数和返回值的预期类型，但默认不会在运行时强制检查。

```python
age: int = 18
age = "hello"  # Python 运行时不会因为类型注解而报错
```

类型注解的主要作用：

- **静态类型检查**：Mypy、Pyright 等工具可以提前发现类型错误。
- **IDE 智能提示**：自动补全、参数提示、类型推断。
- **代码可读性**：明确字段、参数与返回值的预期类型。
- **供框架使用**：Pydantic、FastAPI、dataclass 等可以读取类型注解并提供额外功能。

**核心结论：类型注解 ≠ 运行时类型验证。**

## 二、dataclass 与 BaseModel

### 1. dataclass 是什么？

`dataclass` 是 Python 标准库提供的装饰器，主要用于简化数据类定义。

```python
from dataclasses import dataclass

@dataclass
class User:
    name: str
    age: int
```

它会自动生成 `__init__`、`__repr__`、`__eq__` 等方法（具体取决于配置）。

但是，标准库 `dataclass` 默认不进行运行时类型验证。

```python
user = User(name="Tom", age="18")

print(user.age)        # "18"
print(type(user.age))  # str
```

### 2. Pydantic BaseModel 是什么？

`BaseModel` 是 Pydantic 提供的数据模型基类。

```python
from pydantic import BaseModel

class User(BaseModel):
    name: str
    age: int
```

Pydantic 会根据类型注解执行运行时验证，并在允许的情况下进行类型转换。

```python
user = User(name="Tom", age="18")

print(user.age)        # 18
print(type(user.age))  # int
```

如果无法转换：

```python
User(name="Tom", age="abc")
# ValidationError
```

### 3. 两者的区别

| 特性 | dataclass | BaseModel |
|---|---|---|
| 定义数据结构 | 支持 | 支持 |
| 自动初始化 | 支持 | 支持 |
| 类型注解 | 支持 | 支持 |
| 运行时类型验证 | 默认不支持 | 支持 |
| 自动类型转换 | 不支持 | 支持 |
| 字段约束校验 | 需自行实现 | 支持 |
| 自定义验证器 | 需自行实现 | 内置支持 |
| 序列化 | `asdict()` | `model_dump()` |
| JSON Schema | 不内置 | 支持 |

Pydantic 还提供：

```python
from pydantic.dataclasses import dataclass
```

这种 dataclass 也具备 Pydantic 的验证能力，但与 `BaseModel` 的 API 不完全相同。

### 4. 如何选择？

- **dataclass**：适合内部业务数据、轻量数据对象。
- **BaseModel**：适合 API 请求与响应、JSON 解析、外部数据验证。
- **BaseSettings**：适合环境变量、`.env`、数据库连接等应用配置。
- **Pydantic dataclass**：希望保留 dataclass 风格，同时使用 Pydantic 验证能力。

## 三、Pydantic 的 Model 是什么？

**Model（模型）** 是定义数据结构和验证规则的类。

**Model Instance（模型实例）** 是根据模型类创建的具体对象。

```python
class User(BaseModel):
    name: str
    age: int

user = User(name="Tom", age=18)
```

- `User`：模型类。
- `user`：模型实例。
- `name`、`age`：模型字段。

之所以叫 Model，是因为它描述了一种数据结构及其约束规则，而不仅仅是普通 Python 对象。

`model_validator` 中的 Model 指的是整个数据模型的验证范围，并不代表所有验证模式都操作已经构建好的实例。

## 四、Pydantic 内置类型验证

Pydantic 自身的验证包含：

1. **类型检查**：检查值是否满足字段声明的类型。
2. **类型转换**：例如 `"30"` 转换为 `30.0`。
3. **字段约束校验**：例如大于 0、字符串最小长度。
4. **复合类型验证**：例如 `list[str]`、`Literal`、联合类型。

示例：

```python
from pydantic import BaseModel, Field

class Config(BaseModel):
    timeout: float = Field(
        default=60,
        gt=0,
        allow_inf_nan=False
    )
```

执行：

```python
Config(timeout="30")   # 成功，转换成 30.0
Config(timeout="-10")  # 失败，不满足 gt=0
Config(timeout="abc")  # 失败，无法转换为 float
```

常见约束：

| 约束 | 含义 |
|---|---|
| `gt=0` | 大于 0 |
| `ge=0` | 大于等于 0 |
| `lt=100` | 小于 100 |
| `le=100` | 小于等于 100 |
| `min_length=8` | 最小长度为 8 |
| `max_length=32` | 最大长度为 32 |
| `allow_inf_nan=False` | 不允许无穷大与 NaN |

对于固定取值，可以使用 `Literal`：

```python
from typing import Literal

log_level: Literal[
    "DEBUG", "INFO", "WARNING", "ERROR", "CRITICAL"
] = "INFO"
```

这样不需要额外编写自定义验证器。

## 五、field_validator 与 model_validator

Pydantic V2 提供两种主要的装饰器式自定义验证器。

### 1. 核心区别

| 对比 | field_validator | model_validator |
|---|---|---|
| 验证范围 | 指定字段 | 整个模型 |
| 主要用途 | 单字段业务规则 | 跨字段关联与整体校验 |
| after 模式的参数 | 已验证的字段值 | 已构建的模型实例 |
| 默认 mode | `after` | 必须显式指定 |
| 支持模式 | before、after、plain、wrap | before、after、wrap |

### 2. field_validator

用于验证某一个或多个指定字段。

```python
from pydantic import BaseModel, field_validator

class User(BaseModel):
    age: int

    @field_validator("age")
    @classmethod
    def validate_age(cls, value: int) -> int:
        if value < 18:
            raise ValueError("必须年满18岁")
        return value
```

特点：

- 针对指定字段执行。
- 默认 `mode="after"`。
- 可以验证，也可以修改字段值。
- 验证后的值需要通过 `return` 返回。

### 3. model_validator

用于验证整个模型。

```python
from typing import Self
from pydantic import BaseModel, model_validator

class Settings(BaseModel):
    llm_base_url: str | None = None
    llm_api_key: str | None = None

    @model_validator(mode="after")
    def validate_settings(self) -> Self:
        if self.llm_api_key and not self.llm_base_url:
            raise ValueError(
                "llm_base_url is required"
            )
        return self
```

特点：

- 能访问整个模型的字段。
- 适合多个字段之间的依赖校验。
- `mode="after"` 接收模型实例 `self`。
- `Self` 表示当前类的实例类型。
- 通常返回 `self`。

## 六、Validator 的 mode 执行时机

### 1. field_validator 的四种模式

| mode | 执行时机 | 主要用途 |
|---|---|---|
| before | 内置字段验证之前 | 清洗原始数据 |
| after | 内置字段验证之后 | 自定义业务校验 |
| plain | 替代后续内部验证流程 | 完全自定义验证 |
| wrap | 包裹内部验证流程 | 控制执行、处理异常 |

**before 示例：**

```python
@field_validator("age", mode="before")
@classmethod
def validate_age(cls, value):
    if value == "":
        return 0
    return value
```

输入 `""` 时，可以先转换成 `0`，随后交给 Pydantic 验证。

**after 示例：**

```python
@field_validator("age", mode="after")
@classmethod
def validate_age(cls, value: int) -> int:
    if value < 18:
        raise ValueError("年龄不能小于18")
    return value
```

此时接收到的是通过 Pydantic 内置验证的 `int` 值。

**plain 示例：**

```python
@field_validator("age", mode="plain")
@classmethod
def validate_age(cls, value):
    return value
```

`plain` 会终止字段内部验证流程，不会自动执行后续 Pydantic 类型验证，所以必须自行确保返回结果符合预期。

**wrap 示例：**

```python
@field_validator("age", mode="wrap")
@classmethod
def validate_age(cls, value, handler):
    print("验证之前")
    result = handler(value)
    print("验证之后")
    return result
```

`handler(value)` 用于调用被包裹的内部验证流程。也可以选择不调用它，或者捕获验证异常。

### 2. model_validator 的三种模式

| mode | 执行时机 | 处理对象 |
|---|---|---|
| before | 模型字段验证前 | 原始模型输入 |
| after | 模型字段验证成功后 | 已构建的模型实例 |
| wrap | 包裹模型验证流程 | 输入数据及验证处理器 |

**before 示例：**

```python
@model_validator(mode="before")
@classmethod
def validate_input(cls, data):
    return data
```

输入一般是字典，但并不保证总是字典，也可能是其他类型或模型实例。

**after 示例：**

```python
@model_validator(mode="after")
def validate_model(self) -> Self:
    return self
```

此时可以通过 `self` 访问所有已验证的字段。

### 3. 验证执行顺序

典型模型的执行流程：

```text
传入原始输入
    ↓
model_validator(before)
    ↓
field_validator(before)
    ↓
Pydantic 字段类型转换与约束验证
    ↓
field_validator(after)
    ↓
模型实例构建完成
    ↓
model_validator(after)
    ↓
验证成功，返回模型实例
```

注意：

- 这是不考虑 `plain`、`wrap`、多个验证器嵌套时的简化流程。
- 字段验证失败后，该字段的 `after` 通常不会执行。
- 存在字段验证错误时，模型的 `after` 验证器通常不会执行。
- `mode="after"` 表示相关验证阶段之后，不代表对象初始化函数已经成功返回。
- 模型默认不会在后续属性赋值时重新验证，可通过 `validate_assignment=True` 配置。

## 七、其他验证器

Pydantic V2 还提供基于 `Annotated` 的验证器：

- `BeforeValidator`
- `AfterValidator`
- `PlainValidator`
- `WrapValidator`

示例：

```python
from typing import Annotated
from pydantic import BaseModel, AfterValidator

def positive(value: int) -> int:
    if value <= 0:
        raise ValueError("必须大于0")
    return value

PositiveInt = Annotated[
    int,
    AfterValidator(positive)
]

class Settings(BaseModel):
    timeout: PositiveInt
    max_concurrency: PositiveInt
```

优势是可以重复使用相同的字段验证规则。

Pydantic V1 中的 `@validator`、`@root_validator` 在 V2 中已弃用，通常应迁移到 `field_validator`、`model_validator`。

## 八、BaseSettings 与配置验证

`BaseSettings` 是基于 Pydantic 模型的配置管理类，通常从 `pydantic-settings` 导入。

```python
from pydantic_settings import (
    BaseSettings,
    SettingsConfigDict,
)

class Settings(BaseSettings):
    model_config = SettingsConfigDict(
        env_file=".env",
        extra="forbid"
    )

    database_url: str
    log_level: str = "INFO"
```

相比 `BaseModel`，它额外提供配置来源管理能力，例如：

- 读取环境变量。
- 读取 `.env` 配置。
- 处理默认配置。
- 解析环境变量中的复杂类型。
- 验证最终配置数据。

**BaseSettings 的简化执行流程：**

```text
读取环境变量 / .env / 默认值
              ↓
      整合并预处理配置
              ↓
     Pydantic 模型验证
              ↓
       自定义 Validator
              ↓
      构建 Settings 对象
```

实际执行时，字段级和模型级验证器嵌入 Pydantic 验证过程，并不是所有 Validator 都在实例构建后统一执行。

需要注意：`BaseSettings` 默认会验证字段的默认值，而普通 `BaseModel` 默认不验证默认值。

对于数据库密码、API Key 等敏感配置，可以使用 `SecretStr`，避免在普通对象展示中直接暴露明文。

## 九、Pydantic 的实践原则

优先级建议：

**类型注解 → Field 约束 → field_validator → model_validator**

例如：

```python
class Settings(BaseSettings):
    log_level: Literal[
        "DEBUG", "INFO", "WARNING", "ERROR", "CRITICAL"
    ] = "INFO"

    timeout: float = Field(
        default=60,
        gt=0,
        allow_inf_nan=False
    )

    max_concurrency: int = Field(default=4, gt=0)
```

这里直接使用类型注解和 `Field` 就能完成验证，没有必要再写自定义 Validator。

选择原则：

1. **类型规则**：使用 `int`、`str`、`Literal`、`list` 等类型注解。
2. **长度、范围等简单约束**：使用 `Field`。
3. **单字段复杂规则**：使用 `field_validator(mode="after")`。
4. **需要清洗输入**：使用 `field_validator(mode="before")`。
5. **跨字段关联校验**：使用 `model_validator(mode="after")`。
6. **复用验证逻辑**：使用 `Annotated` 和对应验证器。
7. **特殊验证控制需求**：考虑 `wrap` 或 `plain`。

尽量避免将所有单字段校验集中到一个巨大的 `model_validator` 中，否则会影响代码的职责划分和维护性。

## 十、核心知识总结

**1. Python typing**

类型注解主要描述预期类型，不会自动强制进行运行时验证。

**2. dataclass**

使用类型注解识别字段，自动生成初始化等方法，默认不校验类型。

**3. Pydantic BaseModel**

在模型定义基础上增加运行时验证、类型转换、序列化等能力。

**4. Pydantic BaseSettings**

在 Pydantic 模型基础上提供环境变量、`.env` 等配置读取能力。

**5. field_validator**

针对指定字段执行自定义校验，默认在字段内置类型验证之后执行。

**6. model_validator**

针对整个模型执行自定义校验，尤其适合字段之间的关联规则。

**7. mode**

控制自定义验证器与 Pydantic 内置验证流程的相对执行位置。

**8. 最重要的工程原则**

能用类型注解表达的规则，不必编写额外验证器；能用 `Field` 表达的约束，也不必编写复杂的自定义校验逻辑。
